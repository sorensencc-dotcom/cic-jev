## What was delivered

A standalone local HTTP service, `cic-jev`, that reimplements TypeSafe's
System One (`noul`/`choice`/`score`) request/response contract on top of a
local Ollama model, interoperable with the published `fast-jev-compaction`
npm client. No TypeSafe/Jev source, prompts, or weights copied — behavior
reimplemented from the public client's own request shape (spec
`docs/meta/spec-local-jev-engine.md` §1).

**Files:**
- `src/main.js` — entrypoint. Reads `JEV_MODEL`/`JEV_PORT`/`JEV_OLLAMA_BASE_URL`
  from env (defaults `qwen2.5:7b` / `4173` / `http://127.0.0.1:11434`).
  `npm start` runs it; SIGINT/SIGTERM shut down cleanly.
- `src/server.js` — `createServer({ model, ollamaBaseUrl, fetchImpl })`.
  `POST /v1/systemone` validates the request (size cap, question count cap,
  reserved-id rejection against prototype pollution), calls Ollama, returns
  `{ answers, meta }`. Handles client disconnect mid-request without crashing.
- `src/ollamaClient.js` — `askOllama(...)`. Loopback-only enforcement
  (`assertLoopback`), schema-constrained `/api/chat` call (`format` field,
  `stream: false`), `redirect: 'error'`, AbortController timeout.
- `src/answers.js` — parses Ollama's structured JSON into `noul`/`choice`/`score`
  answers plus a self-reported-certainty confidence heuristic
  (`(certainty - 1) / 4`), labeled `self-reported-heuristic` — NOT a
  calibrated probability (spec §2.3).
- `src/schema.js` — `RESERVED_QUESTION_IDS`, JSON-Schema builders per question
  type.
- `test/*.test.js` — 43 tests, all passing (`npm test`).
- `scripts/smoke-test.mjs` (`npm run smoke`) — one real-Ollama call exercising
  all three question types in one request.
- `scripts/eval-confidence.mjs` (`npm run eval-confidence`) — validates the
  confidence heuristic against a 10-item labeled set
  (`docs/meta/confidence-eval-set.json`), 0.7 accuracy threshold. Observed
  7/10-8/10 across runs (real-model non-determinism, both pass).
- `scripts/verify-client-compat.mjs` (`npm run verify-client-compat`) — live
  proof the published `fast-jev-compaction` `JevClient` round-trips through
  this server against a real Ollama call.
- `docs/meta/MODEL_RESEARCH.md` / `MODEL_DECISION.md` — why v1 runs
  `qwen2.5:7b` (a stock instruct model) instead of a purpose-built Jev model:
  `NanoJev`/`decider` aren't pullable from Ollama (manifest doesn't exist),
  `Verdict` is encoder-only and incompatible with `/api/chat`.

## How it works from now on

1. Start it: `npm start` in `C:\dev\cic-jev` (needs local Ollama running,
   `qwen2.5:7b` pulled). Listens on `127.0.0.1:4173` by default.
2. Any client that speaks the TypeSafe System One contract — including the
   real `fast-jev-compaction` npm package — points its `baseUrl` at
   `http://127.0.0.1:4173/v1/systemone` and just works. The client's `model`
   field is ignored; the server always uses its own configured model.
3. Global safety constraint: the server only ever talks to Ollama over
   loopback (`127.0.0.1`/`localhost`/`::1`), enforced in code, not just docs.
4. Confidence field is a heuristic, not a calibration guarantee — don't treat
   it as safety-grade for gating decisions (e.g. shell command approval)
   without further validation. This is why the shell-safety-gate integration
   below is still a non-goal, not a shipped feature.
5. To verify health after any change: `npm test` (unit, 43 tests, fast, no
   Ollama needed — uses `fetchImpl` mocks) then `npm run smoke` (needs real
   Ollama, confirms end-to-end).
6. Nothing here integrates with any other repo yet. It's a standalone
   service. `toolforge`/kb-sync do not call it.

## Deferred: 3 follow-up specs to write in a NEW session

Per spec §4, none of these are built. Each needs its own spec, written after
grepping the real integration point in *its own* repo — do not assume the
original design draft's guesses (`modules/cache/vector-store.mjs`,
`triageGapAgainstCache()`) still hold; already confirmed those specific names
don't exist in `toolforge` as of 2026-09-21.

1. **Shell safety gate / `jev-guard` fork** — gate agent shell commands on a
   `noul`/`score` decision from this engine. Blocked until confidence
   heuristic has more validation than one 10-item eval set — right now
   gating real commands on it would be a safety regression. Spec must state
   the actual accuracy bar required before this is safe to wire up.
2. **`fast-jev-compaction` compactor plugin wiring** — point the existing
   published compactor at this engine via `baseUrl` instead of cloud Jev.
   Mechanically simple (client already proven interoperable, Task 6/11) but
   still needs a spec for which repo/tool actually uses the compactor and
   how `baseUrl` gets configured there.
3. **kb-sync RAG chunk filter integration** — use this engine to
   triage/filter retrieved chunks before they enter context. Needs the real
   kb-sync structure grepped fresh in `toolforge/kb-sync/` (shape unconfirmed
   as of this spec) before any integration point is assumed.

No llama.cpp/vLLM raw-logit path either (spec §4) — revisit only if Ollama
latency is measured as a real bottleneck, not preemptively.
